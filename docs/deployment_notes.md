# Deployment notes — what changes before this touches a real submission

Everything in this repository was built and evaluated against synthetic data
generated by `src/generate/`. That was a project constraint from day one
(constraint 1: no real personal or tax data, ever), not an oversight to fix
later. This document is for whoever signs off moving from that synthetic
build to a pilot on real ESQ submissions — an Information Governance
reviewer, a DPO, or a technical lead — and lists what has to happen first,
with a pointer to where in the codebase each item lives.

None of this is a formality. Several of these are hard gates, called out as
such in the phase reports as they were built; this document collects them in
one place for a go-live decision, rather than leaving them scattered.

## 1. A DPIA, before anything else

This tool processes special-category-adjacent and financially sensitive data
about identifiable individuals (a worker's name, company details, day rate,
working arrangements) for the purpose of flagging inconsistencies that bear
on a legal determination. That is a Data Protection Impact Assessment
trigger under UK GDPR Article 35 on its own terms, independent of anything
else in this document — automated processing of personal data at scale,
feeding into a decision with legal effect for the individual, is exactly the
kind of processing a DPIA exists to assess *before* it starts, not
retrospectively once a pilot is already running on real data.

The DPIA should cover, at minimum: the residual re-identification risk after
de-identification (item 2 below), the retention period and access controls
for the reviewer decision log (item 4), the legal basis for processing the
worker's data through this tool specifically (as distinct from the ESQ
process it sits inside, which presumably already has one), and — because
Article 22 is central to this project's whole design (see the README's
"Scope and posture" section and every phase report) — an explicit statement
that no automated decision is made and a description of the human review
step that makes that true in practice, not just in the code.

**Note on Phase 7 (tick-box consistency checks and "materiality"):** neither
addition changes this section's assessment. The consistency checks
(`src/models/cross_field.py`) read the same already-in-scope tick-box
answers the Phase 5 flags already read — no new field, and no new category
of data, is processed. Materiality (`src/review/materiality.py`) reads only
two static config files (`config/review.yaml`, `config/ir35_weights.yaml`)
and never the record being reviewed at all — a fact a test asserts
structurally, not just behaviourally, by checking the function's signature
has no parameter a record or a score could be passed through (see
`docs/reports/phase7_consistency_and_materiality.md`). So there is nothing
in Phase 7 for the DPIA to re-scope: the residual re-identification risk,
the data processed, and the human-decision posture described above are
unchanged.

## 2. De-identification: validated against real text, not assumed

`src/deidentify/` is a real, tested pipeline component, run on every
record including the synthetic ones — that was constraint 3, and it is
implemented as a live stage rather than a comment specifically so that this
paragraph does not have to say "this hasn't been exercised yet." But tested
against synthetic text is not the same claim as validated against real
text, and the gap matters here specifically:

- The synthetic generator writes names, companies and figures from closed,
  known vocabularies. The de-identifier's gazetteer-and-pattern approach
  therefore looks better on synthetic data than it will on real free text,
  where a manager writes a name, nickname, or identifying detail the
  detectors have never seen and cannot parse (`src/deidentify/detectors.py`
  is explicit about this limitation in its own docstring).
- **Before this touches real submissions**, run the de-identifier against a
  sample of real (or realistically messy — free-hand, informally worded)
  ESQ text, with a human checking recall by hand: what got missed, and how
  often. `src/deidentify/deidentifier.py`'s `DeidentificationReport` already
  reports counts and affected fields in a form suitable for that check; it
  was built with this validation step in mind, but the step itself has not
  happened, because there is no real text available to run it against yet.
- **Set an acceptable residual-risk threshold before the pilot, not after.**
  If the validation run finds recall below whatever bar Information
  Governance sets, that is a blocker, not a note for a future iteration.

## 3. The local-only backend requirement, enforced not assumed

Constraint 2 of this project's brief assumes production is local-only:
justification text should never leave the University's infrastructure for
inference. The code supports this today, but the config as committed does
not enforce it by default:

- `config/model.yaml` currently sets `require_local: false`. **Before any
  pilot on real data, set this to `true`.** With it set, constructing a
  `hosted_api` backend raises immediately (`BackendUnavailable`,
  `src/models/backend.py`) rather than failing at the first real inference
  call — tested by `test_require_local_blocks_the_hosted_backend` in
  `tests/test_backend_and_detectors.py`.
- `src/models/backend.py`'s `HostedApiBackend` also refuses to send text
  matching an identifier pattern (`_check_deidentified()`), as a second,
  independent backstop. That backstop is not a substitute for
  `require_local: true` — it catches an obviously-unredacted value, not a
  policy decision about whether the hosted path should be reachable at all.
- If the IR35 team's pilot only ever uses the rule baseline, the TF-IDF
  baseline, or a local transformer model (all local by construction), this
  item is about closing a door that should be shut, not about changing which
  detector is used day to day.

## 4. The reviewer decision log: retention and access

`src/review/decision_log.py` writes an append-only JSONL file
(`data/reviewer_decisions/decisions.jsonl` by default, see
`config/review.yaml`) with a reviewer's identity, a timestamp, which flag was
actioned, and — unless configured off, which is the default — a digest
rather than the full text of any note a reviewer typed. This was built as
"the right amount of engineering for a synthetic-data prototype": trivially
inspectable, no running service required, explicitly not proposed as the
production design (see `docs/reports/phase5_interface_report.md`, "Rejected
alternative").

Before real reviewer decisions about real people are recorded in it:

- **Decide a retention period** and implement it — this file has none today,
  it simply grows. A DPIA (item 1) should set this, not a code default.
- **Move it to something with access control.** A flat file on disk that
  anyone with shell or filesystem access can read is not appropriate for a
  log that will contain a University staff member's professional judgement
  about a named worker's submission, however lightly redacted. A database
  with row-level access control, or at minimum filesystem permissions scoped
  to the reviewing team, is the minimum bar.
- **Decide whether `log_reason_content` should ever be `true` in
  production.** The default is `false` (digest only) for the same reason
  `config/pipeline.yaml`'s `logging.log_content` defaults off — a reviewer's
  free-text reason can describe a real person's circumstances as easily as
  the manager's original justification can. Turning it on trades an audit
  benefit (a human-readable reason, later) against a real increase in what
  the log holds; that is an Information Governance decision, not a
  convenience toggle to flip because full text would be more useful.

## 5. A monitoring plan for drift

Two things can change under this tool without any code changing:

- **The ESQ form itself.** `config/schema.yaml` is the single source of
  truth for field names, routing and value domains specifically so that a
  revised form is a config edit (constraint 5) — but a config edit still has
  to happen, and someone has to notice the form changed. Recommend: whoever
  owns the ESQ template notifies whoever maintains this tool's config before
  a revision goes live, not after a submission fails validation in
  production. `src/ingest/validate.py`'s `value_not_in_domain` and
  `answered_off_route` findings will surface a form/config mismatch, but
  only once real submissions are already flowing through a stale config.
- **HMRC guidance and case law.** `config/ir35_weights.yaml` encodes a
  transparent approximation of the case-law weighting behind CEST, used only
  to label the synthetic training corpus — it is never consulted when
  scoring a real submission (see the README's "Scope and posture" and
  `src/models/cest_rules.py`'s own docstring on this exact point). It does
  not need updating for the reviewer app to keep working. It **would** need
  updating if this project is ever extended to generate a fresh synthetic
  corpus reflecting new guidance, or if a future phase reintroduces some
  form of automated status *signal* (which, per Article 22 and this
  project's whole posture, is a decision that should not be made lightly or
  by a code change alone).
- **The detectors' own performance on real submissions**, once a pilot is
  running. Every metric in `docs/reports/phase2_baseline_report.md` and
  `docs/reports/phase4_evaluation_report.md` was measured on synthetic text
  with template-authored phrasing; real managers will write things the
  synthetic generator's vocabulary never produced. Recommend: track flag
  volume, and the accept/dismiss ratio from `src/review/decision_log.py`,
  as an early real-world signal — a sustained high dismiss rate on a
  particular pair or contradiction type is the practical version of the
  "reviewer fatigue" precision floor discussed in
  `docs/reports/phase4_evaluation_report.md`, and is worth reviewing
  periodically (quarterly is a reasonable starting cadence) rather than only
  when someone complains.

## Summary checklist

A pilot on real ESQ submissions should not start until all of these are
true, not just planned:

- [ ] DPIA completed and signed off (item 1).
- [ ] De-identifier recall validated against real or realistic free text,
      against an agreed threshold (item 2).
- [ ] `config/model.yaml`: `require_local: true` (item 3).
- [ ] Reviewer decision log moved off a flat file, with a retention period
      and access control agreed (item 4).
- [ ] A named owner for the ESQ schema/config relationship, and an agreed
      review cadence for flag volume and accept/dismiss rates (item 5).
