# LOCKFILE — exact, transitively-pinned environment for requirements.txt.
#
# requirements.txt pins this project's DIRECT dependencies, with a comment
# next to each explaining why it is there. This file pins EVERYTHING that
# resolves underneath them too (Jinja2, click, pandas, pyarrow, and the rest
# of Streamlit's own dependency tree, etc.) at the exact versions this was
# tested against, so "pip install" cannot quietly pick up a newer transitive
# release that changes behaviour — the same reproducibility argument
# requirements.txt already makes for its own direct pins, extended all the
# way down.
#
# Generated by installing requirements.txt into a bare virtual environment
# (nothing else on the machine, no unrelated packages) and freezing it:
#
#   python3 -m venv /tmp/lockenv && /tmp/lockenv/bin/pip install --upgrade pip
#   /tmp/lockenv/bin/pip install -r requirements.txt
#   /tmp/lockenv/bin/pip freeze | sort > requirements-lock.txt
#   # then this header was added by hand.
#
# Regenerate the same way after any change to requirements.txt, and after
# confirming (see docs/reports/phase6_handover_report.md) that the full test
# suite still passes from that same clean environment — a lockfile that
# reproduces a broken install is worse than no lockfile.
#
# Does NOT cover requirements-transformers.txt, deliberately: torch's build
# is machine-specific (CPU vs a particular CUDA version), so locking it
# centrally would either be wrong for most machines or would force everyone
# onto one build. Anyone installing that file should freeze their own
# environment afterwards if they need to reproduce it exactly.
#
# To install from this file instead of requirements.txt:
#   pip install -r requirements-lock.txt
